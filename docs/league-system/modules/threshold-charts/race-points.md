# Race Points Chart

A peer variant of the **[Threshold Charts](README.md)** Module — a [Chart](../../PRINCIPLES.md#chart--deep-dive)-kind Module.

> **Reading this cold?** A threshold chart is a passive lookup table (or formula) that converts a handicap input into a concrete match-setup benchmark. This page describes the **Race Points Chart** variant: a discrete 2D table that takes a pair of individual player handicaps (Points encoding) and returns the per-pairing race-to game-win target for each player. Other Chart variants exist (see the [Module README](README.md) for the full picture).

## What it is

A **discrete 2D table**, looked up by **both players' exact handicaps**, that returns the race-to target for each player in a single one-on-one pairing. Unlike team-aggregate Charts that consume only the *difference*, this Chart consumes **both absolute handicaps** — the skill level of the players matters, not just the gap between them. The chart is calibrated for individual matchups where the handicap encoding is the [Points](../handicap-systems/points.md) (-2 to +2 integer) system.

**Picture this** (for the novice-explanation case): Player A is a +2 (strong); Player B is a -1 (weak). You look up the cell where row=+2 meets column=-1 and the chart tells you: "Player A races to 6 wins; Player B races to 3 wins; first to their target wins this pairing." The chart adjusts the asymmetry both by the *gap* between players and by the *skill tier* the stronger player sits in.

## How it works / how it's calculated

**Input:** **two integers** — `(handicap_higher, handicap_lower)`, the two paired players' Points handicaps. The chart is stored as the upper triangle only (where `handicap_higher >= handicap_lower`); when the actual pairing has the lower-handicap player on the home side, the lookup swaps the result columns to maintain the right per-side mapping.

**Output:** a 2-tuple of integers: `(race_higher, race_lower)`.

- `race_higher` — the race-to game-win target for the *higher-handicap* (stronger) player.
- `race_lower` — the race-to game-win target for the *lower-handicap* (weaker) player.

First to their target wins the pairing. (At even matchups, the two targets are equal — both players race to the same number.)

**Lookup is exact on both axes.** Both handicaps must be exact values in the supported range (here, -2 to +2). The match between row and column is direct equality.

**Why two axes instead of one (gap only).** A *gap of 2* between a +2 and a 0 (Row: 2 vs 0 → 6-4) is **not** the same pairing as a gap of 2 between a 0 and a -2 (Row: 0 vs -2 → 5-3). Both gaps are 2, but the lower-skill pairing happens at a lower base race because lower-skill players reach lower game counts in a fixed match window. The 2D lookup encodes this skill-tier effect; a 1D gap-only chart can't.

**Calibration algorithm sketch** (informational, not policy): the chart was generated by an algorithm with three parameters — `base race` at top tier (5), `max race` ceiling (7), `min race` floor (2 or 3). The base race decreases by 1 per skill tier below the top. Within a row, the gap-1 adjustment subtracts 1 from the lower player; the gap-2 adjustment adds 1 to the higher player; gaps alternate this pattern. When the lower-player target would dip below the floor, the adjustment overflows to extending the higher player's race instead. The shipped chart is the materialized output of this algorithm.

## When you'd use it / pros

- **Native fit for per-pairing handicapping with the [Points](../handicap-systems/points.md) encoding.** The 2D lookup captures the skill-tier effect a team-aggregate Chart can't see.
- **Operator-readable as a printed grid** — 15 rows for the +2 to -2 Points range. Players can be shown the grid and immediately see "I'm here, my opponent is here, we race to these numbers."
- **Skill-floor protection** — the minimum-race floor prevents weaker players from being put on absurdly short races (1-game or 2-game races where luck dominates skill).
- **Per-pairing scope produces fairer individual matchups** than a team-aggregate threshold for leagues where the lineup-pairing decisions matter.

## When you wouldn't / cons

- **Tied to the [Points](../handicap-systems/points.md) encoding's small integer range.** Pairing with Percentage or FargoRate requires either the [Race Percentage Chart](race-percentage.md) (sister variant for Percentage encoding) or a [Converter](../../PRINCIPLES.md#converter--deep-dive).
- **Per-pairing scope only.** A league wanting one threshold for the whole match (team-aggregate) needs a team-scope Chart instead.
- **No interpolation** — handicaps outside the supported range have no answer.
- **The grid is fixed-size** — extending to a wider Points range requires regenerating the whole 2D table.

## Interactions

- **Upstream:** consumes the per-player handicaps produced by the [Points](../handicap-systems/points.md) Handicap System for both players in a pairing.
- **Consumed by:** the [Race Length Adjustment](../handicap-mechanisms/race-length-adjustment.md) Handicap Mechanism, which reads the 2-tuple and declares the asymmetric per-pairing race lengths.
- **Sibling variant:** the [Race Percentage Chart](race-percentage.md) — same scope (per-pairing) and shape (2D), different encoding (Percentage instead of Points).
- **Not directly pairable** with the [FargoRate](../handicap-systems/fargorate.md) or [Skill Level](../handicap-systems/skill-level.md) encodings without a [Converter](../../PRINCIPLES.md#converter--deep-dive).

## Possible modifications

- **Base / max / min race parameters** — the algorithm's three knobs. Lower base = shorter races (more variance, faster matches); higher base = longer races (skill expression dominates more).
- **Cell-level edits** — overrides for individual `(higher, lower)` handicap pairs if an LO wants a specific cell tuned away from the algorithmic default.
- **Range extension** — add rows/columns for handicaps beyond ±2 if the league uses an extended Points scale.
- **Round-trip caveat:** the algorithm can re-generate the whole table from the three parameters. Once cell edits diverge from the algorithm's output, the chart is persisted as a stored table and can no longer be regenerated from the parameters alone. (Per [PRINCIPLES § Chart — § 4](../../PRINCIPLES.md#4-formula-first-charts-are-derived).)

- **Schema:** `threshold_charts` + `threshold_chart_rows` (`comp_1` = higher player handicap, `comp_2` = lower player handicap, `result_1` = higher player race, `result_3` = lower player race, `result_2` = null) in `supabase/migrations/20260410000002_threshold_charts.sql`. The SQL `lookup_threshold()` function performs the cascade and 2D lookup.
- **Algorithm helper:** `calculateRaceLengths()` (or similarly named) helper in `src/utils/handicap/` — generates the default rows from `(base, max, min)` parameters. Used to seed the chart and (per-LO) to regenerate cells when parameters change.
- **Consumer wiring:** not currently wired to a shipped Scoring System (the three shipped Scoring Systems all use team-aggregate Charts). The Chart is scaffolded for future per-pairing race-mode Scoring Systems. **This is expected scaffolding** — the Module exists for the design space, not for the shipped wiring. Step-2+ work will wire it to a per-pairing race-mode Scoring System when one is built.
