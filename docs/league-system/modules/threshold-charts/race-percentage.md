# Race Percentage Chart

A peer variant of the **[Threshold Charts](README.md)** Module — a [Chart](../../PRINCIPLES.md#chart--deep-dive)-kind Module.

> **Reading this cold?** A threshold chart is a passive lookup table (or formula) that converts a handicap input into a concrete match-setup benchmark. This page describes the **Race Percentage Chart** variant: a discrete 2D table that takes the gap between two players and the stronger player's skill tier (Percentage encoding), and returns the per-pairing race-to game-win target for each player. Other Chart variants exist (see the [Module README](README.md) for the full picture).

## What it is

A **discrete 2D range table**, looked up by **(handicap gap bracket, stronger-player skill tier bracket)**, that returns the race-to target for each player in a single one-on-one pairing. Like the [Race Points Chart](race-points.md), this Chart consumes more than just the gap — it also factors in the stronger player's absolute skill tier — but it does so via *brackets* rather than exact handicap values. The chart is calibrated for individual matchups where the handicap encoding is the [Percentage](../handicap-systems/percentage.md) (0–100 integer) system.

**Picture this** (for the novice-explanation case): Player A is at 85 percentage; Player B is at 50. The gap is 35; the stronger player's tier is 74–100. You look up the cell where "gap 32–47" meets "tier 74–100" and the chart tells you: "Player A races to 6 wins; Player B races to 4 wins; first to their target wins this pairing." Brackets keep the chart small and operator-readable while still capturing both the gap effect and the skill-tier effect.

## How it works / how it's calculated

**Input:** **two integers** — `(gap, highest_handicap)`:

- `gap` — the absolute difference between the two players' Percentage handicaps.
- `highest_handicap` — the *stronger* (higher Percentage) player's handicap value.

**Output:** a 2-tuple of integers: `(race_higher, race_lower)`.

- `race_higher` — the race-to game-win target for the *higher-handicap* (stronger) player.
- `race_lower` — the race-to game-win target for the *lower-handicap* (weaker) player.

First to their target wins the pairing.

**Lookup is range-based on both axes.** The chart stores rows where:

- `comp_1` = the **gap bracket's upper bound** (e.g., 16 means *"gaps 0–15"*; 32 means *"gaps 16–31"*).
- `comp_2` = the **skill tier's lower bound** (e.g., 74 means *"highest handicap 74–100"*; 47 means *"highest handicap 47–73"*).

The lookup finds the row whose gap bracket contains the input gap AND whose tier bracket contains the input highest handicap. Both brackets must match. With 5 gap brackets × 3 skill tiers, the shipped table is 15 rows.

**Why brackets instead of exact rows.** Percentage's 0–100 range creates a huge 2D input space (potentially 100 × 100 = 10,000 exact cells) that no operator could read or tune. Bracketing into 15 meaningful cells preserves the structural insights (gap matters, skill tier matters) without an unreadable matrix.

**Why the skill-tier axis.** Just like with [Race Points](race-points.md): a gap of 30 between an 85 and a 55 player is **not** the same pairing as a gap of 30 between a 45 and a 15 player. The lower-skill pairing happens at a lower base race because lower-skill players reach lower game counts in a fixed window. The 2D lookup captures this; a 1D gap-only chart can't.

**Calibration algorithm sketch** (informational): the chart was generated by the same algorithm shape as Race Points — three parameters (`base`, `max`, `min` race) plus a division count for the gap brackets. Tier count is derived from `base - min + 1`; tier ranges divide the handicap span evenly. Within a tier row, gap brackets alternate adjustments (subtract from lower, then add to higher); when adjustments would push past the min/max floors/ceilings, the algorithm overflows to the other player.

## When you'd use it / pros

- **Native fit for per-pairing handicapping with the [Percentage](../handicap-systems/percentage.md) encoding.** The 2D bracketing keeps a wide-range encoding readable.
- **Operator-readable grid** — 15 cells the LO can post or print and reason about row-by-row.
- **Skill-floor protection** — minimum-race floor prevents absurdly short races for low-skill players.
- **Per-pairing scope produces fairer individual matchups** than a team-aggregate threshold for leagues where lineup-pairing decisions matter.

## When you wouldn't / cons

- **Tied to the [Percentage](../handicap-systems/percentage.md) encoding's range space.** Pairing with Points or FargoRate requires either the [Race Points Chart](race-points.md) (sister variant for Points encoding) or a [Converter](../../PRINCIPLES.md#converter--deep-dive).
- **Per-pairing scope only.** A league wanting one threshold for the whole match (team-aggregate) needs a team-scope Chart instead.
- **Coarse-grained on both axes** — gap of 17 and gap of 30 produce the same targets if they're in the same bracket; same for skill tiers. Operators wanting finer-grained tuning need a Chart with more buckets, or a formula-shaped variant.
- **The grid is fixed-size** — changing tier count or bracket count requires regenerating the whole table.

## Interactions

- **Upstream:** consumes the per-player handicaps produced by the [Percentage](../handicap-systems/percentage.md) Handicap System for both players in a pairing.
- **Consumed by:** the [Race Length Adjustment](../handicap-mechanisms/race-length-adjustment.md) Handicap Mechanism, which reads the 2-tuple and declares the asymmetric per-pairing race lengths.
- **Sibling variant:** the [Race Points Chart](race-points.md) — same scope (per-pairing) and shape (2D), different encoding (Points instead of Percentage).
- **Not directly pairable** with the [FargoRate](../handicap-systems/fargorate.md) or [Skill Level](../handicap-systems/skill-level.md) encodings without a [Converter](../../PRINCIPLES.md#converter--deep-dive).

## Possible modifications

- **Base / max / min race parameters** — the algorithm's three knobs.
- **Gap bracket count and boundaries** — finer or coarser brackets along the gap axis.
- **Tier bracket count and boundaries** — finer or coarser tiers along the skill axis.
- **Cell-level edits** — overrides for individual `(gap bracket, tier bracket)` cells if an LO wants a specific cell tuned away from the algorithmic default.
- **Round-trip caveat:** the algorithm can re-generate the whole table from its parameters. Once cell edits diverge from the algorithm's output, the chart is persisted as a stored table and can no longer be regenerated from the parameters alone. (Per [PRINCIPLES § Chart — § 4](../../PRINCIPLES.md#4-formula-first-charts-are-derived).)
