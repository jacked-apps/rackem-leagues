# Message Push Notifications — Requirements

**Date:** 2026-08-18
**Suggested branch:** `feat/message-push-notifications`
**Status:** Requirements captured. Ready for planning.
**Relationship to prior work:** This is a scoped, standalone extraction of **Phase 2** of
`docs/brainstorms/2026-04-21-messaging-system-overhaul-requirements.md`. That doc bundled push with
rate-limiting, quiet hours, notification pause, and live-match bypass. This feature deliberately ships
push *loud and controls-light first*, then builds the controls from observed pain (see §7).

---

## 1. Overview

### Problem

The messaging system's foundation shipped (Phase 1: auto-created team/captain/announcement chats,
mute controls, in-app unread badges). Real users are now using it and have **asked for a chime when
someone messages them.** Today the app has no way to reach a phone that isn't actively open — new
messages are only knowable via an in-app badge while the app is focused. Users who aren't looking at
the app miss messages entirely, so coordination leaks back out to SMS.

### What we're building

Web Push notifications so a new message produces a **phone/desktop notification even when the app is
closed or backgrounded**, and **tapping it jumps straight to that conversation.**

### Deliberate product bet

We ship this **intentionally loud** — push on essentially everything, minimal throttling — because the
test population is a single league of mostly personal friends. The goal is to *provoke* the annoyance
that reveals exactly which chats and cadences need controls, then build the preference panel (§7) from
real pain rather than guesses.

### Scope boundaries

- **In scope (v1):** subscription + permission flow, a custom service worker that shows notifications,
  server-side dispatch on new messages, tap-to-open routing, respect for the **existing** per-chat mute
  and a **global on/off**, and graceful iOS handling.
- **Deferred by decision (v2, see §7):** the user-facing notification **preferences panel** (per-chat
  and frequency controls), and **reply-from-notification** (Android/desktop inline reply).
- **Non-goals (this feature):** rate-limiting, quiet hours, notification-pause duration picker,
  live-match quiet-hours bypass, `@mention`-based routing (mentions aren't built), email notifications.

## 3. Platform realities that shape the product

These are hard constraints, not preferences — the design must absorb them.

1. **iOS delivers push only to installed PWAs.** On iPhone/iPad, Web Push works **only after the user
   adds the app to their home screen.** In a plain Safari tab, Apple sends *nothing*. So on iOS the
   first step is always "Add to Home Screen," and we must detect the not-installed state and nudge,
   rather than silently failing.
2. **Tap-to-open is universal; richer interactions are not.** Every platform supports "tap the
   notification → open the app at the right place." Notification **action buttons and inline reply are
   Android/desktop-Chrome only** — iOS Safari supports neither. This is why reply-from-notification
   (§7) is a platform-gated fast-follow, never a universal feature.
3. **PWA-only project.** There is no native app now or planned. "Push" here means Web Push via a
   service worker throughout.

## 4. Goals & success criteria

**Goals**

1. A user who isn't looking at the app still learns, on their device, that a message arrived.
2. Tapping the notification lands them **in that exact conversation.**
3. Users can turn it **off** (global) and existing per-chat **mute** silences a chat's pushes.
4. iPhone users get a clear path to enable it (install-to-home-screen), not a dead end.
5. The loud-first rollout surfaces concrete "this chat/cadence is too much" pain we can act on.

**Success looks like**

- A friend gets a lock-screen chime for a new DM, taps it, and is reading the message in one motion —
  app was fully closed.
- A user who muted the busy team chat gets **no** pushes from it, while still getting DM pushes.
- An iPhone user who hasn't installed the app sees a friendly "add to home screen to get notified"
  explanation instead of a silently broken toggle.
- Within the first weeks, we can name the top 2–3 annoyance sources (which chats, what times, what
  volume) directly from user reactions — the input to the v2 preferences panel.

**Primary signal (qualitative by design):** we are *looking for* complaints. The point of loud v1 is
that "chat X buzzes too much at hour Y" is the deliverable that shapes v2. Secondary observable proxy:
share of subscribed users who keep push enabled vs. globally disable it in week one.

## 5. Decisions captured (from brainstorm)

| # | Decision | Rationale |
|---|---|---|
| D1 | **Ship loud first, controls second.** v1 pushes on all conversations with no new throttling; the preferences panel is built from the pain v1 surfaces. | Single league of personal-friend testers is the ideal place to provoke and observe annoyance rather than guess at throttling rules. |
| D2 | **Honor the *existing* mute + a global on/off in v1.** No *new* throttling (no rate-limit, quiet hours, or pause). | Mute is an explicit user action already in the schema/UI; ignoring it would be hostile. Honoring it is nearly free. Everything beyond that is v2. |
| D3 | **Tap-to-open is v1 and universal.** Notification tap deep-links to the specific conversation. | Works on every platform; it's the core of the ask. |
| D4 | **Reply-from-notification is deferred to v2, Android/desktop only.** | Bigger build (background send with auth in the service worker), and iOS can never show it. Not worth blocking the loud-phone experiment. |
| D5 | **iOS not-installed state is handled explicitly**, with an "Add to Home Screen" nudge, not a silent no-op. | iOS Web Push requires PWA install; a broken-looking toggle would erode trust. |
| D6 | **The v2 preferences panel is a known, planned direction, not a maybe.** It fits the app's "a preference for everything" pattern and reuses the existing `notification_mode` tri-state. | User explicitly wants user-tunable controls; v1 is scoped so as not to foreclose it. |
| D7 | **Permission ask piggybacks on the existing first-open messaging onboarding.** | There's already a first-Messages-open modal (profanity); adding the push ask there is lower-friction than a settings scavenger hunt. Exact copy/placement is a planning detail. |

## 6. Feature requirements (v1)

### 6.1 Subscribe & permission

- On an appropriate trigger (default: the existing first-Messages-open onboarding, per D7), ask the
  browser for notification permission and register a push subscription.
- Store the subscription per user so the server can target their device(s); a user may have several
  (phone + laptop). Multiple devices per user is expected and supported.
- Handle every permission outcome: granted, denied, dismissed, unsupported browser, and **iOS-not-yet-
  installed** (D5) — each gets appropriate in-app copy and next step.
- A **global on/off** control in Messages settings so a user can disable all push without touching the
  browser-level permission.

### 6.2 Delivery

- When a new message is inserted, the server figures out **who should be notified** and pushes to their
  subscribed devices.
- **Recipient selection (v1, loud):** every participant of the conversation *except the sender*, minus
  anyone whose membership is muted (`notification_mode = 'none'` or legacy `is_muted`) and minus anyone
  with global push off. No other filtering.
- **Notification content:** sender name + a short message preview + the conversation name where useful.
  Preview text must respect the **recipient's** profanity-filter preference (filtering is per-user and
  the server assembles the payload). Consider a privacy fallback ("New message") as a future per-user
  option — not required for v1.
- Delivery is best-effort: a failed/expired subscription is cleaned up, not retried forever.

### 6.3 Tap-to-open

- Tapping the notification opens (or focuses) the app **at that conversation** — if the app is already
  open, focus it and navigate; if closed, launch to that conversation.
- Works identically across platforms (this is the one interaction iOS fully supports).

### 6.4 Service worker

- A **custom** service worker (the current setup auto-generates one with no push logic) that handles
  the `push` event (show the notification) and the `notificationclick` event (focus/navigate).
- Must coexist with the existing PWA/offline caching the plugin provides — not replace it.

## 7. Deferred by decision — the v2 controls (documented, not built now)

These are **planned**, shaped by what v1's loud rollout teaches us. Captured here so planning treats
v1 as a foundation, not a dead end.

- **Notification preferences panel** — per-conversation choice (all / mentions / mute) surfaced in UI
  (the `notification_mode` column already backs this), plus frequency/cadence controls (e.g., "first
  message then quiet for N minutes"), and likely quiet-hours. **The specific controls are intentionally
  unspecified until v1 shows which pain is real.**
- **Reply-from-notification** (D4) — Android/desktop inline reply: the service worker sends the reply on
  the user's behalf without opening the app. The inline reply box itself is one line of `showNotification`
  options on Android; the real work is **authenticated background send** (the service worker posting a
  message as the user while the app is closed). **Ed has confirmed this is wanted later** — so v1 should
  be built to make it cheap, without building it now (see §7.1).

### 7.1 Forward-compatibility for reply-from-notification (do in v1, at ~zero extra cost)

These are choices v1 needs anyway; making them deliberately means the later reply feature is mostly a
service-worker code change, not a re-architecture. **None of this builds the reply feature now.**

- **Push payload carries `conversation_id`.** v1 already needs this for tap-to-open routing; the same
  identifier is the reply target later. Include enough context to both open *and* answer the thread.
- **`push_subscriptions` maps endpoint → member/user server-side.** v1 needs this to know who to notify.
  That same mapping lets a future reply endpoint authenticate "this device belongs to member X" from the
  subscription itself — avoiding the hard problem of getting the user's login session into the service
  worker. Treat the subscription as the device's identity.
- **One custom service worker owns the notification lifecycle.** v1 builds it for `push` +
  `notificationclick`. Reply later is an added `actions: [{ action: 'reply', type: 'text' }]` plus a
  reply branch in the same handler — no new worker.
- **Plan note (not v1 work):** the reply sink will be a **server-side send path** (Edge Function or DB
  RPC) that inserts a message for a member identified by their subscription. Don't assume message-send is
  client-only forever; keep the send-side rules (participant check, profanity-stores-original,
  system-message shape) reachable server-side so the future endpoint can reuse them.
- Prior art for the fuller version lives in Phase 2 of
  `docs/brainstorms/2026-04-21-messaging-system-overhaul-requirements.md` (rate-limit window, quiet
  hours 10pm–7am, pause duration picker, live-match bypass). Treat it as a menu to pull from once pain
  is observed — not a spec to implement wholesale.

## 8. Defaults & assumptions (confirm or override in planning)

1. Permission ask lives in the existing first-Messages-open onboarding flow (D7).
2. Notification shows sender + preview (profanity-filtered per recipient); no privacy-hide mode in v1.
3. "Loud" = notify all non-sender participants who haven't muted and haven't globally disabled.
4. Multiple devices per user supported; expired subscriptions pruned on send failure.
5. VAPID keys are secrets (env/secret store), never committed.
6. All current app data is disposable test data — no backfill/migration concerns for existing chats.

---

## 9. Open questions for planning

- **Dispatch mechanism** — DB trigger + `pg_net` → an Edge Function, vs. an Edge Function subscribed to
  realtime message inserts, vs. client-initiated. Pick in planning based on reliability/latency.
- **Service worker strategy** — moving `vite-plugin-pwa` from `generateSW` to `injectManifest` (custom
  SW source) vs. another registration approach that preserves existing caching. Planning decision.
- **iOS install nudge placement** — inside the onboarding modal only, or also a persistent hint on the
  push toggle when iOS + not-installed is detected.
- **Push payload privacy** — is a "hide preview on lock screen" toggle worth including as a small v1
  extra, or strictly v2?
- **VAPID / token ownership** — this project is PWA-only, so web is the sole holder; confirm no mobile-
  partner coordination is needed (the older overhaul doc assumed a shared APNs/FCM track that no longer
  applies).
